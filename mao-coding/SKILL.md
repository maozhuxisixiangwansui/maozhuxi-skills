# 毛泽东思想编程法

> "马克思主义的哲学认为，对立统一规律是宇宙的根本规律。这个规律，不论在自然界、人类社会和人们的思想中，都是普遍存在的。"——毛泽东

软件工程的本质，是**人在认识世界与改造世界过程中所形成的矛盾运动**。代码不是数学公式，而是社会实践的产物——它有阶级性（服务谁？），有矛盾性（性能 vs 可读性、灵活 vs 稳定），有阶段性（MVP → 优化 → 重构）。本方法论以毛泽东哲学思想为指导，把软件工程从"经验主义—教条主义"的两极拉回到**辩证唯物主义**的轨道上来。

---

## 一、世界观：你写的代码是什么？

> "辩证法唯物论是无产阶级的宇宙观，同时又是无产阶级认识周围世界的方法和革命行动的方法，它是宇宙观和方法论的一致体。"

**三个基本判断**（任何工作开始前必须明确）：

1. **代码是客观世界的反映，不是头脑中虚构的产物**——离开了真实需求与生产环境，所谓"优雅架构"只是观念论的幻象。
2. **代码是运动的、发展的，没有"最终版本"**——你写的每一行都注定要被修改、替换、删除。把代码当成"永恒不变的真理"，就是形而上学。
3. **代码内部充满矛盾，矛盾推动它发展**——性能 vs 可维护性，抽象 vs 具体，灵活 vs 稳定。否认矛盾、回避矛盾，就是回避工程本身。

**反对两种倾向**：
- ❌ **唯心论编程**：先验地相信某个框架/范式（"Clean Code 万能""微服务一切""TDD 必须"），不从实际需求出发
- ❌ **机械唯物论编程**：照搬最佳实践、生搬硬套设计模式，不分析具体矛盾的特殊性

## 二、《矛盾论》在编程中的运用（核心方法）

### 1️⃣ 一分为二：任何代码都有两面性

> "事物都是一分为二的。"

**编程中的"一分为二"清单**：

| 看待对象 | 正面 | 反面 |
|---------|------|------|
| 一段"漂亮"的代码 | 易读、抽象优美 | 可能过度设计、隐藏成本 |
| 一个"成熟"的库 | 稳定、生态好 | 锁死技术栈、迁移成本高 |
| 一次"成功"的上线 | 用户增长、好评 | 掩盖了潜在债务 |
| 一个"高效"的同事 | 速度快、产出多 | 是否积累了维护负担？ |
| 一份"完美"的设计 | 考虑周全 | 可能脱离实际、过度工程 |

**操作要点**：评审代码、做技术决策时，强制问自己——"这件事的对立面是什么？我是否只看到了一面？"

### 2️⃣ 主要矛盾：用全力找出它

> "研究任何过程，如果是存在着两个以上矛盾的复杂过程的话，就要用全力找出它的主要矛盾。捉住了这个主要矛盾，一切问题就迎刃而解。"

**编程实践映射**：

- **性能优化**：永远先用 profiler 找瓶颈。**主要矛盾在数据库慢查询时，优化前端动画就是教条主义**。
- **Bug 修复**：症状（异常报错）≠ 根因。沿着堆栈、日志、数据流，找到那个"牛鼻子"——一个根因往往修复一片症状。
- **架构重构**：不要面面俱到。**找出最痛的那个点**（部署慢？测试不稳？模块耦合？）集中力量打透。
- **需求拆解**：MVP 不是减法，是**对主要矛盾的精确识别**——哪个功能是用户来这里的唯一理由？

**反例**："这个项目所有地方都要改"——这是没有主要矛盾意识的表现，会导致全面铺开、处处受阻。

### 3️⃣ 矛盾的主要方面：决定事物性质

> "事物的性质，主要的是由取得支配地位的矛盾的主要方面所规定的。"

**编程映射**：
- 一个系统是 **"读多写少"** 还是 **"写多读少"**？决定缓存策略与数据库选型。
- 一个团队是 **"经验主导"** 还是 **"流程主导"**？决定工具链与规范。
- 一个项目当前阶段是 **"探索期"** 还是 **"稳定期"**？决定能否激进重构。

**判断口诀**：定性之前先定主要方面，定主要方面之前先做调查。

### 4️⃣ 矛盾的特殊性：具体问题具体分析

> "对于具体的事物作具体的分析。"
> "一把钥匙开一把锁。"

**编程铁律**：
- 没有"放之四海皆准"的最佳实践
- 同样是"微服务"，电商和 IM 的拆分原则完全不同
- 同样是"重构",遗留系统和新项目的策略截然相反
- 同样是"性能优化"，CPU 密集与 IO 密集是两种逻辑

**操作模板**——任何"标准方案"应用前，先回答四个问题：
1. 这个方案诞生的**原始矛盾**是什么？
2. 我现在面对的**特殊矛盾**是什么？
3. 这两组矛盾有**多大重合度**？
4. 不重合的部分，方案会带来什么**新矛盾**？

### 5️⃣ 内因与外因：变化的根据与条件

> "外因是变化的条件，内因是变化的根据，外因通过内因而起作用。"

**编程深刻含义**：
- **代码质量问题的内因**，是团队的工程素养、设计思维；**外因**是 lint 工具、CI 检查。**没有内因，工具治标不治本**。
- **重构失败的内因**，是对原系统理解不透；**外因**是时间压力。**理解不透时，给再多时间也重构不好**。
- **bug 难调的内因**，是不变量被破坏、抽象出错；**外因**是缺日志。**不分析内因，加再多日志也是雾里看花**。

**口诀**：**先内后外，先里后表**。不要用工具去掩盖思维的懒惰。

### 6️⃣ 量变与质变：促成转化

> "我们要善于观察和分析事物，发现它矛盾的两个方面，并促成事物的转化。"

**编程映射**：
- **小步重构 → 架构跃迁**：连续 100 次 5 分钟级别的小改动，能完成一次别人眼中"不可能"的迁移
- **TDD 的本质**：测试-代码-重构的微循环，是量变；当覆盖率与可测性到达临界，代码会发生质变（敢于大改）
- **技术债务的反面**：当 PR 大小、构建时间、bug 数量超过阈值，团队效率会**陡崖式**下降——这是质变

**警戒线**：警惕"还差一点点"——量变积累到临界点，质变是突发的，不会发邮件提前通知你。

### 7️⃣ 矛盾的同一性与斗争性：对立面的统一

> "矛盾着的对立面又统一，又斗争，由此推动事物的运动和变化。"

**编程映射**：
- 性能与可读性**斗争**着，但在好的抽象里**统一**于"清晰意图"
- 灵活与稳定**斗争**着，但在好的接口设计里**统一**于"职责分离"
- 速度与质量**斗争**着，但在好的工程文化里**统一**于"持续交付"

**反对形而上学**：把任何二元对立绝对化（"性能党 vs 可读派""左派静态语言 vs 右派动态语言"），就是放弃寻找统一的辩证可能。

## 三、《实践论》在编程中的运用

> "实践，认识，再实践，再认识，这种形式，循环往复以至无穷，而实践和认识之每一循环的内容，都比较地进到了高一级的程度。"

### 编程的认识论循环

```
   原始需求（感性认识）
        ↓
   原型/Spike（第一次实践）
        ↓
   领域抽象（理性认识）
        ↓
   正式实现（第二次实践，受抽象指导）
        ↓
   生产反馈（认识被检验）
        ↓
   重构（更高一级的理性认识）
        ↓
   ... 循环往复
```

**纪律性原则**：
1. **没有调查就没有发言权**——没读过代码、没看过日志、没复现过 bug，不要发表意见
2. **实践是检验真理的唯一标准**——再优雅的设计，没在生产环境跑过都是假设
3. **从感性到理性，从理性到实践**——先做调研，再总结模式，再落地代码；跳步就会翻车
4. **认识的飞跃靠实践**——读 100 篇博客不如自己实现一次

### 反对两种错误

- **教条主义编程**：搬运 Hacker News 的最佳实践，不结合项目实际
- **经验主义编程**：只凭"上次我是这么做的"，不上升到原理与抽象

## 四、调查研究：编程的方法论起点

> "你对于那个问题不能解决么？那么，你就去调查那个问题的现状和它的历史吧！你完完全全调查明白了，你对那个问题就有解决的办法了。"

### 编程"调查"清单（接到任何任务前）

- [ ] **代码考古**：`git log`、`git blame`、近 6 个月的相关 PR、issue
- [ ] **历史决策**：架构文档、ADR、设计文档、过去的失败方案
- [ ] **运行实况**：日志、监控、性能数据、错误率、用户反馈
- [ ] **使用者声音**：内部用户、外部客户、客服反馈、社区讨论
- [ ] **依赖现状**：依赖库版本、上下游服务、外部 API 限制
- [ ] **团队约定**：编码规范、Review 流程、发布机制、值班约定

**没做这六项调查就动手——就是主观主义。**

### 实事求是

> "'实事'就是客观存在着的一切事物，'是'就是客观事物的内部联系，即规律性，'求'就是我们去研究。"

- 不要"我觉得"——拿出数据、拿出日志、拿出 benchmark
- 不要"应该可以"——跑一遍、测一遍、量一遍
- 不要"差不多"——精确的事情精确地做

## 五、军事辩证法在编程中的运用

### 1️⃣ 战略上藐视，战术上重视

> "在战略上藐视一切敌人，在战术上重视一切敌人。"

- **战略上**：再难的系统不过是 if/else 和数据流转。不要被规模、术语、技术神秘感吓住。
- **战术上**：每一行 SQL 都可能慢查询，每一个 nil 指针都可能崩溃。落到键盘上要如履薄冰。

### 2️⃣ 集中优势兵力，各个歼灭敌人

> "伤其十指不如断其一指。"

- 不要同时开 10 个分支——选一个最关键的打透
- 不要同时优化所有性能瓶颈——按 80/20 集中火力打 Top 3
- 不要同时学 5 个新技术——选一个深入到能教别人

### 3️⃣ 你打你的，我打我的

> "打得赢就打，打不赢就走。"

- **不要被技术流行**牵着走。竞品用 K8s 不代表你必须用——你的业务规模可能根本不需要
- **不要被"标准答案"**绑架。面试题答案 ≠ 生产实践
- **打不赢就走**：撞墙的方案换思路，**沉没成本不是继续的理由**

### 4️⃣ 持久战：技术债务的真相

> "战略上的持久战，战役战斗上的速决战。"

- 技术债务不可能"一次性还清"——这是速胜论的幻想
- 也不能"放任不管"——这是逃跑主义
- 正确路线：**长期作战 + 每次冲刺中的小胜**——每个 sprint 偿还 5%，连续做 20 个 sprint
- **不打无准备之仗**：大重构前必须建立"根据地"——测试、文档、监控

### 5️⃣ 农村包围城市

> "在敌强我弱的总形势下，先在敌人薄弱的环节建立根据地。"

**遗留系统改造模板**：
1. 不要从核心模块开刀（敌人最强处）
2. 从**外围工具、监控、文档、辅助脚本**开始建立"根据地"
3. 在根据地中沉淀**自动化测试、CI、可观测性**——这是装备和补给
4. 由外围向中心**逐步包围**——重构边界模块、再到核心
5. 最后**决战**于核心代码——此时弹药、地形、士气都已具备

## 六、群众路线：用户与团队

> "从群众中来，到群众中去。"

### 编程中的"群众"

- **真正的群众**：你的用户、运维同事、值班工程师、客服、未来接手代码的人
- **不是群众**：技术大 V、Hacker News、面试官、你自己的审美

### 群众路线工作法

1. **从群众中来**：用户反馈、日志埋点、A/B 测试结果、bug 报告，是你设计的起点
2. **集中起来**：把零散的痛点抽象成**统一的领域模型**
3. **到群众中去**：用代码解决他们的问题，再观察反馈
4. **再循环**：永远把使用者放在抽象之前

**反对两种倾向**：
- ❌ **尾巴主义**：用户要什么做什么，没有抽象、没有判断
- ❌ **命令主义**：闭门造车设计"我觉得最好的"，强加给用户

## 七、矛盾的两类：敌我矛盾与人民内部矛盾

> "敌我之间和人民内部这两类矛盾的性质不同，解决的方法也不同。"

### 编程映射

| 矛盾类型 | 编程对应 | 处理方式 |
|---------|---------|---------|
| 敌我矛盾 | 安全漏洞、致命 bug、数据损坏 | **专政**——立即修复、彻底消灭、回滚保护 |
| 人民内部矛盾 | 代码风格分歧、技术选型争论、性能取舍 | **民主**——讨论、说服、试验、求同存异 |

**严重错误**：
- 把人民内部矛盾当敌我矛盾——团队为 tab/空格吵翻
- 把敌我矛盾当人民内部矛盾——对安全漏洞"我们讨论讨论"

## 八、批评与自我批评：代码评审

> "有则改之，无则加勉。"
> "惩前毖后，治病救人。"

### Code Review 的态度

- **对事不对人**：批代码不批人
- **既要批评又要团结**：指出问题是为了改进，不是为了证明高明
- **自我批评先行**：先反思自己的代码，再去评审别人
- **群众路线**：评审是 Review 者与 Author 共同认识代码的过程

### 整风：周期性反思

- 每个 sprint/季度做一次**整风**：
  - 哪些决策事后看是错的？根源何在？
  - 哪些"经验"已成了束缚？需要打破？
  - 团队是否陷入了某种**形式主义**（开会、文档、流程为了存在而存在）？

## 九、工作流模板：用毛泽东思想完成一个工程任务

```
阶段一：调查研究（实事求是）
  ├── 读代码、读历史、读数据
  ├── 听用户、听同事、听客服
  └── 输出：现状报告（不带"我觉得"）

阶段二：矛盾分析（一分为二）
  ├── 列出所有矛盾
  ├── 找出主要矛盾
  ├── 判断矛盾的主要方面
  └── 输出：问题诊断书

阶段三：制定方针（具体问题具体分析）
  ├── 战略：长期方向（持久战）
  ├── 战术：本次行动（集中兵力）
  ├── 路线：从外围到核心
  └── 输出：行动计划

阶段四：实践（实践—认识—再实践）
  ├── 小步快跑、量变积累
  ├── 每步验证、实事求是
  ├── 出错就调头、不教条
  └── 输出：可工作的代码

阶段五：总结提高（批评与自我批评）
  ├── 复盘哪些假设错了
  ├── 提炼可复用的认识
  ├── 写入 ADR / 知识库
  └── 输出：上升到理性的总结
```

## 十、操作清单（每次写代码前贴在屏幕旁）

- [ ] 我做了**调查研究**了吗？还是凭印象？
- [ ] 我找到**主要矛盾**了吗？还是面面俱到？
- [ ] 我**具体问题具体分析**了吗？还是套模板？
- [ ] 我考虑了**内因**了吗？还是只想加工具？
- [ ] 我**一分为二**看自己的方案了吗？还是只看好处？
- [ ] 我准备了**根据地**（测试/监控）了吗？还是裸奔？
- [ ] 我的**主要矛盾**和**次要矛盾**没搞反吧？
- [ ] 我准备打**持久战**还是幻想速胜？
- [ ] 我是为**群众**（用户）写代码，还是为自己的审美？

## 附：禁忌清单

❌ "这个框架别人都用"——盲目跟风，没有矛盾的特殊性意识
❌ "应该不会出问题"——主观主义，不做调查
❌ "我们一次性把它做对"——速胜论，否认矛盾发展过程
❌ "这个不是我们的问题"——逃跑主义，不敢面对矛盾
❌ "改不动了，推倒重来"——形而上学，不分内因外因
❌ "代码规范就是真理"——教条主义，把工具当本体
❌ "用户不懂他们要什么"——脱离群众，主观主义
